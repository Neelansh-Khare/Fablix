# FabFlix Technical Analysis (2025-11-12)

This document provides a detailed technical analysis of the FabFlix web application, covering its architecture, component interactions, data flow, and potential areas for improvement.

## 1. Project Overview

FabFlix is a Java-based web application for browsing and managing a movie database. It appears to be a student or portfolio project, demonstrating a classic Model-View-Controller (MVC) architecture using Java Servlets, JSP, and a MySQL database. The application provides features for user authentication, movie browsing, searching, and an administrative interface for data management.

### Key Technologies:
- **Backend:** Java 23, Java Servlets, JSP
- **Frontend:** HTML, CSS, JavaScript (jQuery)
- **Database:** MySQL (inferred from `mysql-connector-j`)
- **Build Tool:** Apache Maven
- **Key Libraries:**
    - `javax.servlet-api`: For building web components.
    - `mysql-connector-j`: For database connectivity.
    - `org.json`: For handling JSON data in servlets.
    - `dom4j`: For XML parsing (data import).
    - `commons-codec`: For password hashing.
    - `HikariCP`: For database connection pooling.
    - `reCAPTCHA`: For bot protection on login/registration.

## 2. Architecture and Design

The application follows a layered architecture:

- **Presentation Layer (View):** Implemented with JSP (`index.jsp`) and dynamically rendered content via JavaScript. The frontend is a Single Page Application (SPA) where content is loaded into the `#content-container` div.
- **Controller Layer:** Java Servlets (`/api/*`) handle all incoming HTTP requests. They process user input, interact with the service layer, and return JSON responses.
- **Service Layer:** Encapsulates business logic (e.g., `MovieService`, `CustomerService`). It acts as a bridge between the controllers and the data access layer.
- **Data Access Layer (DAO):** Consists of DAO interfaces (`MovieDAO`, `CustomerDAO`, etc.) and their implementations (`MovieDAOImpl`, `CustomerDAOImpl`). This layer is responsible for all database interactions.
- **Model Layer:** Plain Old Java Objects (POJOs) like `Movie.java`, `Customer.java`, etc., represent the data structures of the application.
- **Utility Layer:** Contains helper classes for database connections (`DBConnectionUtil`), security (`SecurityUtil`), and external API interactions (`MoviePosterUtil`).

## 3. Component Interaction and Data Flow

### 3.1. User Authentication
1.  **UI:** The user enters credentials in a modal form (`login-modal`).
2.  **JavaScript (`auth.js`):** Captures the form data and a reCAPTCHA token.
3.  **AJAX Request:** A POST request is sent to `CustomerServlet` with the action `login`.
4.  **Servlet (`CustomerServlet`):**
    - Verifies the reCAPTCHA token using `RecaptchaUtil`.
    - Applies rate limiting per IP address using `RateLimiterUtil`.
    - Calls `CustomerService.login()`.
5.  **Service (`CustomerService`):** Calls `CustomerDAO.verifyPassword()`.
6.  **DAO (`CustomerDAOImpl`):**
    - Retrieves the salt and hashed password for the given email from the `customers` table.
    - Hashes the user-provided password with the retrieved salt using `SecurityUtil.hashPassword()`.
    - Compares the generated hash with the stored hash.
7.  **Response:** The servlet creates an HTTP session if the login is successful and returns a JSON success message. The frontend updates the UI to show the user's account information.

### 3.2. Movie Browsing and Search
1.  **UI:** The user interacts with the search bar or browse links.
2.  **JavaScript (`main.js`, `autocomplete.js`):**
    - For search, `autocomplete.js` sends requests to `AutocompleteServlet` as the user types.
    - A full search request is sent to `SearchServlet`.
    - Browsing by genre/letter sends requests to `SearchServlet`.
3.  **Servlets (`SearchServlet`, `MovieServlet`):**
    - Receive search/browse criteria.
    - Call the appropriate method in `MovieService` (e.g., `searchMovies`, `getMoviesByGenre`).
4.  **Service (`MovieService`):**
    - Calls the corresponding method in `MovieDAO` to fetch movies from the database.
    - **Asynchronously fetches movie posters:** It checks if a movie lacks a valid poster URL and, if so, triggers an asynchronous call to `MoviePosterUtil.searchMoviePoster()` to fetch a poster from The Movie Database (TMDB) API. This is a good design choice to avoid blocking the user's request.
5.  **DAO (`MovieDAOImpl`):** Executes SQL queries to retrieve movie data. It uses `PreparedStatement` to prevent SQL injection.
6.  **Response:** The servlet formats the movie list as a JSON array and sends it to the frontend.
7.  **JavaScript (`main.js`):** `displayMovies()` function renders the movie cards on the page.

### 3.3. Data Import (ETL)
- The `XMLDataImporter.java` class provides a command-line utility to import movie and star data from XML files.
- It uses `dom4j` for parsing and interacts with the `MovieService` and `StarService` to persist the data.
- This is a separate process and not part of the web application's runtime flow.

## 4. Potential Bugs and Areas for Improvement

### 4.1. Security
- **SQL Injection:** The use of `PreparedStatement` throughout the DAOs is excellent and effectively mitigates SQL injection risks. **No major vulnerabilities found here.**
- **Password Storage:** Passwords are salted and hashed with SHA-256. This is good, but a stronger, more modern hashing algorithm like **Argon2** or **scrypt** would be an improvement over a fast hash function like SHA-256.
- **API Keys:** The TMDB API key and reCAPTCHA secret key are hardcoded in the Java source files (`MoviePosterUtil.java`, `RecaptchaUtil.java`).
    - **CRITICAL BUG:** This is a major security risk. These keys can be easily extracted from the compiled code.
    - **Recommendation:** Externalize secrets. Use environment variables or a properties file that is *not* checked into version control.
- **Admin Access:** The `PosterUpdateServlet` has a commented-out, very basic admin check. It currently allows any logged-in user to trigger poster updates.
    - **BUG:** This endpoint lacks proper authorization.
    - **Recommendation:** Implement a role-based access control (RBAC) system. Add a `role` column to the `customers` table (e.g., 'user', 'admin') and protect admin servlets with a filter that checks for the 'admin' role.

### 4.2. Database and Concurrency
- **Connection Pooling:** The custom connection pool in `DBConnectionUtil.java` is a manual implementation using a `ConcurrentLinkedQueue`.
    - **BUG/RISK:** This implementation is simplistic and likely not as robust or efficient as a mature, battle-tested connection pool library. It lacks features like connection validation, idle timeout handling, and proper lifecycle management.
    - **Recommendation:** Replace the custom pool with the `HikariCP` dependency that is already included in `pom.xml`. HikariCP is a high-performance, production-ready connection pool.
- **Error Handling:** The DAOs catch `SQLException` and print a stack trace (`e.printStackTrace()`).
    - **Improvement:** This is not ideal for a production application. Errors are swallowed, and the calling layer has no way of knowing that a database operation failed.
    - **Recommendation:** Propagate exceptions up to the service or controller layer. Wrap `SQLException` in a custom runtime exception (e.g., `DataAccessException`) to be handled globally, allowing for proper error responses (e.g., HTTP 500) to be sent to the client.

### 4.3. Frontend
- **JavaScript Dependencies:** The project uses jQuery, which is a bit dated for a modern SPA.
    - **Recommendation:** For a future rewrite, consider a modern frontend framework like React, Vue, or Svelte for better state management and component-based architecture.
- **Cart Implementation:** The shopping cart is implemented entirely in `localStorage`.
    - **Limitation:** This means the cart is tied to a specific browser and device. It won't persist across sessions on different devices.
    - **Recommendation:** For a more robust implementation, store the cart data on the server, associated with the user's session or account.

### 4.4. Code Quality and Maintainability
- **Configuration in `db.properties`:** The `db.properties` file contains placeholder values (`driver`, `url`, `username`, `password`). This indicates the project is not configured to run out-of-the-box.
- **Redundant Code:** The `MovieDAOImpl` has a `deleteStarsInMovie` and `deleteGenresInMovie` method that is called before deleting a movie. If the database schema uses `ON DELETE CASCADE` for foreign keys, these manual deletions would be unnecessary.
- **Lack of Logging:** `e.printStackTrace()` is used instead of a proper logging framework. The project includes `slf4j` and `logback` dependencies, but they are only used in a few places.
    - **Recommendation:** Consistently use a logger (like the `LOGGER` instance in `MovieService`) throughout the application for better diagnostics.

## 5. Summary of Findings

- **Strengths:**
    - Clear, layered architecture.
    - Good use of DAO and Service patterns.
    - Protection against SQL injection.
    - Asynchronous fetching of movie posters to improve UX.
    - Implementation of security features like reCAPTCHA and rate limiting.

- **Critical Issues:**
    1.  **Hardcoded API Keys:** Secrets are exposed in the source code.
    2.  **Inadequate Connection Pooling:** The custom pool is risky and should be replaced with HikariCP.
    3.  **Missing Admin Authorization:** The poster update endpoint is not properly secured.

- **Recommendations for Improvement:**
    1.  **Externalize Secrets:** Move API keys and database credentials out of the codebase.
    2.  **Implement HikariCP:** Refactor `DBConnectionUtil` to use the existing `HikariCP` dependency.
    3.  **Add Role-Based Access Control (RBAC):** Secure administrative endpoints.
    4.  **Improve Exception Handling:** Stop swallowing `SQLException`s and provide meaningful error responses.
    5.  **Adopt a Logging Standard:** Use SLF4J/Logback consistently.
    6.  **Refactor Frontend (Long-term):** Consider migrating from jQuery to a modern frontend framework.
    7.  **Server-Side Cart:** Move cart logic to the backend for a persistent user experience.
